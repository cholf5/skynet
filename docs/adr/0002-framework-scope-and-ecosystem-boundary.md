# ADR 0002：框架边界、生态引用策略与反膨胀纪律

- 状态：已接受（Accepted）
- 日期：2026-09-15
- 关联任务：E 系列（E-1..E-11）收官讨论、F-1
- 备注：本文是本仓库的**范围宪法**，对未来的维护者与自动化贡献者（含 AI agent）同样有约束力。

## 问题陈述

E 系列补齐 PRD 缺口后，项目面临"下一步往哪长"的抉择：在框架上继续叠可拔插中间层
（Skynet.Database、品类基础设施），还是像云风 skynet 一样停在纯粹的基础框架？

讨论中确立的核心担忧：**底层的价值来自克制**。使用者若只是想要 Actor 能力，却被迫
接纳一堆"教人怎么做游戏"的中间层，框架就失去了中立性；而品类设施（AOI、帧同步、
场景管理）与具体设计决策耦合极深，预先设计几乎必然在真实项目面前被迫大改，最终
沦为负资产。同时，即将启动的 OpenMU 移植项目（MMORPG 私服框架）会持续对框架提出
改进诉求，若无边界纪律，"查漏补缺"会变成"查漏补肥"。

## 决策

### 1. 仓库边界：本仓库 = 框架本体

包含且仅包含：Actor 运行时（Core）、集群与传输（Cluster / Transport.Kcp）、网络接入
（Net：Gate/Session/MsgServer）、RPC 源生成器（Generators）、以及**插件接缝的参考实现**
（Extras：DebugConsole、Prometheus 导出、持久化文件存储等）。

不包含：数据库适配、登录/账号体系、匹配、品类设施（MOBA/MMORPG/FPS 的任何共性组件）、
以及一切"只有一个项目才用得上"的东西。

### 2. 准入判据：唯一合理解测试

一件东西能否进入框架，看它**有没有唯一合理解**：

- 有（mailbox 如何排队、帧如何切、RPC 如何序列化）→ 框架收。
- 没有（数据库访问策略、AOI、匹配规则——各有一百种合理做法）→ 框架不收，去向按第 4 条分流。

### 3. 生态项目以 submodule + 工程引用消费框架（已定案）

OpenMU 移植等生态项目通过 **git submodule 引入本仓库、直接工程引用** src 各项目。
不走 NuGet、不走 prerelease feed。理由：移植期与框架共同高频演进，工程引用使改动
原子化、零版本管理开销；发包基础设施（pack/release 流水线）保留但**公开发 NuGet 的
时机由维护者酌情决定，非当前目标**——0.x 阶段发公开包会产生无法撤回的版本包袱。

### 4. 查漏补缺三分类分流（移植项目的发现处置规则）

移植/使用中发现的框架缺口，动手前先归类：

| 分类 | 判据 | 去向 |
|------|------|------|
| 契约级缺口 | 现有插件接缝/核心 API 无法表达某类合法需求 | 改框架（走看板流程 + ADR 评估） |
| 单一可行实现 | 该能力虽有多种做法但本仓库场景下答案收敛 | 独立生态仓库的包/组件，永不进本仓库 |
| 经验而非代码 | 是指导、模式、注意事项 | 写进 docs 作为模式指南 |

### 5. Core 纪律

`Skynet.Core` 的依赖列表与公共 API 表面积：进入 1.0 后**只减不增**；0.x 阶段新增
公共 API 须能通过第 2 条判据。当前 Core 仅依赖 Logging.Abstractions + MessagePack，
此状态是目标状态。

### 6. Extras 的身份：可选参考实现

`Skynet.Extras` 中的组件是"这个接缝怎么用"的示范，**不是框架的一部分**：使用者可以
完全不用 Extras 而自行实现同等能力；Extras 的变更节奏也独立于 Core 的稳定性承诺。
文档与 README 已按此口径标注。

## 后果

- 正面：底层保持小而稳；品类复用通过生态层实现而不污染框架；移植项目的改进诉求有
  明确的处置管道；"哪些代码该不该进本仓库"从此有可引用的裁决依据。
- 代价：真正的品类基础设施需要另起仓库（成本转移到生态层，属预期内）；Extras 的
  "非框架"身份需要文档持续澄清。
- 再评估触发条件：若未来多个生态项目反复出现相同的接缝诉求且现有契约确实无法表达，
  按第 4 条"契约级缺口"通道重新评估——那不是膨胀，是契约演化。
